# 要決定事項と決定の記録

**着手前に §1 を埋める。** 各項目に推奨案を付けてあるので、異論が無ければ「推奨どおり」と書くだけでよい。
決めたら該当する文書の「推奨」を「決定」に書き換え、§3 に日付と理由を残す。

## 0. 判断の前提

開発は Claude Code で進める。したがって **実装の工数・手間を理由にした縮小は行わない。**
範囲を狭める根拠として認めるのは次の 3 つだけ。

1. **製品上の理由**: 原則（`principles.md`）に反する、利用者を迷わせる、検証されていない仮説に立っている
2. **技術的制約**: API・ブラウザ・レートリミットの事実（`../backlog-facts.md`）が許さない
3. **人の判断が要る**: 実機での確認、秘密情報の扱い、ストア提出のように人しかできない工程に依存する

「作ると時間がかかる」「部品が増える」は理由にならない。過去の文書（`mvp:docs/implementation-plan.md` §17 など）が
工数で切ったものは、この基準で見直してある（§3 の 2026-09-13 の記録）。

## 1. 要決定（Phase 1 の UI に効くもの）

### D-1. サイドパネルの役割

- **推奨: 「詳しく見る面」として Phase 1 に含める。** 検索結果はパレットに出す（原則 P8）ので、パネルは検索の面ではなく
  **選択している結果の詳細（本文の抜粋・ハイライト・メタ情報）を出し、結果を保持し、絞り込みを調整する面**にする。
  パレットの選択に追従して中身が変わる。仕様は `surfaces.md` §5
- 別案: パネルを作らない。「開く前に中身を見る」価値を捨てることになり、製品上の理由が無い

### D-2. 検索の起動をどうするか

- **推奨: Enter で明示。** Wiki がプロジェクト単位の並列になるため、全スペースで 1 回の検索が search 枠（150 / 分）を
  数十消費しうる（技術的制約）。IME 変換中の中間文字列で叩く無駄も避けられる
- 別案: 入力停止から 400ms で自動起動。スコープが単一プロジェクトのときだけなら予算に収まる可能性がある。
  M1 の実測（`milestones.md`）で search 枠の消費を測ってから判断する

### D-3. 検索結果をどこに出し、選択をどう動かすか

- **推奨: 検索行の直下にセクションを挿し、起動と同時に選択をプレースホルダ行へ移す。** `語 → ↵ → ↵` で先頭ヒットが開く。
  候補セクションは下に残す
- 別案: 候補を消して結果だけにする。候補にあった行へ戻る操作が要る

### D-4. プロジェクト行の Enter

- **推奨: プロジェクトホームへ遷移。** 「プロジェクトを切り替える」という利用者の言葉に一致する。スコープを狭めたいときは
  `#プロジェクト名` で候補をプロジェクトだけにしてから選ぶのではなく、**検索行の補足に出るスコープ**を `⌫` で広げる方向だけを持つ
- 別案: `›` でスコープに積む。切り替えたいだけの人に 1 打鍵増える（製品上の理由で退ける）

### D-5. コピー後にパレットを閉じるか

- **推奨: 開いたまま、フッターにトーストを 2 秒。** 閉じるとトーストの出し先が無い（パレットは iframe で、ページ側に DOM を作らない。技術的制約）
- 別案: 表示後に自動で閉じる。連続コピーができなくなる

### D-6. Esc はスコープを外すか

- **推奨: 外さない。スコープだけのとき Esc は閉じる。** 「Esc で閉じる」が壊れると逃げ道が無くなる

### D-7. マウスホバーで選択を動かすか

- **推奨: 動かさない。クリックは Enter と同じ。**

### D-8. 開いているときの ⌘K

- **推奨: 閉じる（トグル）。**

### D-9. 絞り込み条件をどこで持つか

- **推奨: 条件は検索状態の一部として持ち、3 つの入口から入る。**
  1. 入力中の語のうち **現在プロジェクトのステータス名と完全一致するもの**を条件として検出し、検索行を 2 つ出す
     （「決済」を 処理中 で検索 ／「処理中 決済」をそのまま検索）。チップを外すキーを増やさず、行を選ぶだけにする
  2. `@名前` で担当者を条件にする（D-12）
  3. サイドパネルの常設フィルターバー（種別・ステータス・担当者・更新日・キーワード対象）。条件はすべて AND、各条件は単一選択、
     OR はプリセット（「完了を除く」）で吸収する
  0 件時の提案は「効いている条件を外す」を先頭に置く
- 別案: パレットにもフィルターバーを置く。キーボードだけで完結する面に選択 UI を足すことになり、P1 に反する

### D-10. Backlog 以外のページで ⌘K を効かせるか

- **推奨: 効かせる。ポップアップとして同じパレットを出す。** スコープは最後に使ったスペース、プロジェクトは無し。
  空状態は最近開いた + 担当中の課題。仕様は `surfaces.md` §6
- 別案: Backlog 上だけ。「どこからでも Backlog に飛べる」を捨てることになり、製品上の理由が無い

### D-11. 文言の多言語化

- **推奨: 日本語と英語を Phase 1 で持つ。** ブラウザの UI 言語に従い、設定で上書きできる。部品は文言を `labels` として受け取り、
  ドメイン語（ステータス名など）は最初から props。ストア掲載文は日英とも確定稿がある（`mvp:docs/reference/backlog-cmdk-extension-plan.md` §10）

### D-12. `@ユーザー` プレフィックス

- **推奨: Phase 1 で持つ。** 候補源は `GET /api/v2/projects/:key/users` を参加プロジェクト分積み上げたもの
  （`GET /api/v2/users` は管理者ロールが要る。技術的制約）。ユーザー行の Enter は **その人を担当者条件にした検索**を起動する。
  担当課題一覧ページの URL は未確認（`backlog-facts.md` §1.2）なので、遷移ではなく検索に接続する

### D-13. 候補リストの挙動レイヤー

- **推奨: `CandidateList` は自前で書く**（`role="listbox"` + `aria-activedescendant`、controlled な選択）。要件が
  「選択は container が持つ」なので、内部状態を持つライブラリと相性が悪い。MVP が react-aria-components で踏んだ 3 つの罠
  （仮想フォーカスの持ち越し・`Escape` の消費・`isComposing` の無視）はいずれもこの相性から来ている
- 別案: react-aria-components を続け、MVP の `surfaceKeys.ts` の対処を全部持ち込む

### D-14. 表示キャッシュの stale-while-revalidate

- **推奨: Phase 1 で入れる。** 表示した行だけを裏で再取得し、ステータス・担当者を差し替える。差し替えで**行の位置は動かさない**

### D-15. ローマ字 → かな変換マッチ

- **推奨: Phase 1 で持つ。** `kadai` → `かだい` → 課題一覧 のように、かなの別名を持つページ・コマンドに英字入力でも届く。
  照合は正規化パイプラインの 1 段として入れる。読みを持たない件名・プロジェクト名には効かない（読みデータが無い。技術的制約）

### D-16. 遷移パターンによる個人化

- **推奨: Phase 1 で持つが、効かせる場所を限る。** 「課題を開いた後はボード」のような共起は、空状態の「{プロジェクト} のページ」
  セクション内の並びにだけ効かせる。介入ルール（セクション順固定・完全一致は動かさない・同点のときだけ）の内側に閉じる

## 2. 決定済み（MVP から継承。理由は `mvp:docs/implementation-plan.md` §3・§19）

| 決定 | 要点 |
|---|---|
| スタックモデル | スコープは列挙値ではなくパス。右端から 1 段ずつ外す。コマンド階層も同じスタック |
| `Tab` は候補の補完 | スコープ切替には使わない。IME と競合し、フォーカスが出る |
| `⌫` の 2 段 | キャレット先頭のときだけスタックに効く。1 回目は予告、2 回目で外す。入力文字は消えない |
| 全スペース検索はフラット | スペース別のグループ見出しを差し込まない。非同期到着で選択が動く |
| 常設フィルターバーは単一選択の AND | Backlog の検索は OR ができない。OR はプリセットで吸収する（サイドパネルに置く。D-9） |
| React + 見た目はトークン層 | 見た目の差し替えはトークンと CSS Modules だけで済む構造 |
| 接続の既定は API キー | OAuth は `scope` も PKCE も無く、権限を絞る利点が無い。OAuth は任意の副経路として持つ（§3） |
| `client_secret` は配布物に含める | RFC 8252 の public client。`redirect_uri` の一致が実質の防御。配布前にローテーションする |
| 直接ジャンプ行・コマンド名完全一致は個人化で動かさない | 筋肉記憶を守る不変条件 |
| セクションの順序は固定 | 個人化はセクション内の並びにだけ効く |
| 認証情報は Service Worker だけが持つ | UI にも content script にも渡さない |

## 4. Phase 2（作らない。理由は工数ではない）

| 項目 | Phase 1 に入れない理由 |
|---|---|
| 課題への書き込み（ステータス変更・担当者・マイルストーン）、お知らせの既読 | 原則 P2。破壊的操作には確認と Undo の設計が要り、その設計を検証する場が Phase 1 の実機評価。読み取り専用で信頼を作ってから |
| 保存済み検索条件の登録 | 課題一覧のクエリ文字列の仕様が未確認（`backlog-facts.md` §5-10）。検索状態の URL 共有（P1 に含む）で代替できるかを見てから |
| チーム共有のカスタムリンク | 共有の置き場（誰が書き、どこに保存するか）が製品として未定義 |
| Backlog 本体の全体検索の代替 | 添付本文など拡張の索引外がある。足りないときは本体へ逃がす方針を維持 |
| Backlog 本体の UI の書き換え | 製品の範囲外 |
