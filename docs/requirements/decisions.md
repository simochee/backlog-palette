# 要決定事項と決定の記録

§1 の 16 件は 2026-09-13 に 1 件ずつ確認して決めた。覆すときは §3 に日付と理由を残し、該当する文書を直す。
新しく決めることが出たら §1 に番号を足す。

## 0. 判断の前提

開発は Claude Code で進める。したがって **実装の工数・手間を理由にした縮小は行わない。**
範囲を狭める根拠として認めるのは次の 3 つだけ。

1. **製品上の理由**: 原則（`principles.md`）に反する、利用者を迷わせる、検証されていない仮説に立っている
2. **技術的制約**: API・ブラウザ・レートリミットの事実（`../backlog-facts.md`）が許さない
3. **人の判断が要る**: 実機での確認、秘密情報の扱い、ストア提出のように人しかできない工程に依存する

「作ると時間がかかる」「部品が増える」は理由にならない。過去の文書（`mvp:docs/implementation-plan.md` §17 など）が
工数で切ったものは、この基準で見直してある（§3 の 2026-09-13 の記録）。

## 1. 決定（2026-09-13、全 16 件を確認済み。M1 着手時に D-17〜D-20、M3 着手時に D-21〜D-23 を追加）

各項目の「別案」は退けた理由とともに残す。覆すときは §3 に記録する。

### D-1. サイドパネルは「詳細検索の面」

- **決定**: パレットは語とスコープだけで探し、サイドパネルは**条件を付けて探す**。本文のプレビューは持たない。中身は Backlog のページで見る。
  結果と検索状態は残る。`⌘→` で語とスコープを引き渡す。仕様は `surfaces.md` §5
- 退けた案: 「詳しく見る面」（本文の抜粋 + ハイライト）。この拡張の範囲で課題の中身まで見せる必要はない、という製品判断
- 退けた案: MVP のまま「モーダル＝行く／パネル＝探す」。実機で否定された前提に戻る

### D-2. 検索は Enter で明示的に起動する

- **決定**: 検索行で `↵`。打鍵ごとに API を叩かない。Wiki がプロジェクト単位の並列になるため、全スペースで 1 回の検索が
  search 枠（150 / 分）を数十消費しうる（技術的制約）
- 退けた案: 単一プロジェクトのときだけ自動起動。M4 で search 枠の消費を実測した後に再検討してよい

### D-3. 検索結果は検索行の直下。選択は先頭結果へ

- **決定**: 検索行の直下に「検索結果」セクションを挿し、起動と同時に選択をプレースホルダ行へ移す。`語 → ↵ → ↵` で先頭ヒットが開く。候補は下に残す

### D-4. プロジェクト行は `↵` で遷移、`⇥` でスコープに積む

- **決定**: `↵` はプロジェクトホームへ遷移。`⇥` はスコープに積む。あわせて **`⇥` の意味を「実行せずに入力欄へ取り込む」で統一**する:
  `space` / `project` / 2 段階コマンドの行は積む、それ以外の行はタイトルで補完する。MVP の裁定 D1（Tab＝補完）はこの一般化に含まれる
- 退けた案: `⌘↵` で積む。`⌘↵` の意味が行によって変わる

### D-5. コピー後はパレットを開いたまま、フッターにトーストを 2 秒

- **決定**: 閉じるとトーストの出し先が無い（パレットは iframe で、ページ側に DOM を作らない。技術的制約）。連続コピーもできる

### D-6. Esc はスコープを外さない

- **決定**: スコープだけのとき `Esc` は閉じる。スコープを外すのは `⌫` の 2 段だけ。コマンド階層では `Esc` で 1 段戻る

### D-7. マウスホバーで選択を動かさない。ただし強調はする

- **決定**: クリックは `↵` と同じ。ホバーは選択（`aria-activedescendant`・罫・太字）を動かさないが、行の面を薄く強調してクリックできることを示す（Raycast と同じ）。
  2026-09-13 の M1 目視で「ホバーしても何も起きない」のは不親切と判断して強調を足した

### D-8. 開いているときの `⌘K` は閉じる

- **決定**: トグル

### D-9. パレットに絞り込み条件を持たない

- **決定**: パレットの検索は語とスコープだけ。種別・ステータス・担当者・更新日の条件はサイドパネルのフィルターバーだけが持つ。
  0 件時にはパレットから「詳細検索で条件を変えて探す」の行でパネルへ渡す
- 退けた案: ステータス名の検出で検索行を 2 つ出す。パレットの役割が曖昧になる

### D-10. `⌘K` は Backlog のページ上だけで効く

- **決定**: 他のサイトの `⌘K` を奪わない（既存機能を損なうサイトがある）。ブラウザの `commands` に既定キーを登録せず、
  Backlog のページの content script で捕捉する。Backlog 外のタブではツールバーのアイコンが設定画面を開く
- 含意: `commands` を使わないので、Backlog 本体のエディタやショートカットとの境界（未決 #4）を M3 の実機確認で決める

### D-11. 日本語と英語を持つ

- **決定**: ブラウザの UI 言語に従い、設定で上書きできる。部品は文言を `labels` として受け取る

### D-12. `@ユーザー` プレフィックスは持たない

- **決定**: スペース全体のユーザー一覧は管理者しか取れない（`GET /api/v2/users`。技術的制約）。プロジェクト単位の積み上げも採らない。
  担当者はサイドパネルのフィルターで「自分／未設定」だけを扱う

### D-13. 候補リストは自前で書く

- **決定**: `role="listbox"` + `aria-activedescendant`、選択は controlled。MVP が react-aria-components で踏んだ 3 つの罠
  （仮想フォーカスの持ち越し・`Escape` の消費・`isComposing` の無視）は内部状態を持つライブラリとの相性から来ている。
  入力欄と競合しない部品（スイッチ・セレクト・ダイアログ）には react-aria-components を使ってよい

### D-14. 表示キャッシュは stale-while-revalidate

- **決定**: 表示した行だけを裏で再取得し、ステータス・担当者・件名を差し替える。行の位置は動かさない。接続済みスペース限定

### D-15. ローマ字 → かな変換マッチを持つ

- **決定**: 正規化の 1 段として入れる。効くのはかなの別名を持つページ・コマンド。読みを持たない件名・プロジェクト名には効かない

### D-16. 遷移パターンによる個人化を持つ

- **決定**: 空状態の「{プロジェクト} のページ」セクション内の並びにだけ効かせる。介入ルール（セクション順固定・完全一致は動かさない・同点のときだけ）の内側

### D-17. Popover・Switch・RadioGroup は Radix Primitives。react-aria-components は採らない

- **決定**: 入力欄を包まない headless primitives として Radix Primitives（`radix-ui`）を使う。用途は フィルターバーの Popover、
  設定画面の Switch、フィルターの RadioGroup。Phase 2 で書き込み操作の確認が要るときは同じ Radix の AlertDialog を足す。
  パレットの listbox・キー処理は D-13 のとおり自前のまま
- 理由: フォーカストラップが要る面は Phase 1 に無い（パレットもシートも iframe。削除の確認は 2 段押し）が、Popover 級の部品
  （位置の反転・スクロール追従・光閉じ・フォーカスの戻し・`aria-expanded` の配線）は毎回同じバグを踏む種類の仕事で、自作しない方がよい。
  Radix は data 属性でスタイルするので Tailwind（D-18）と素直に噛み合い、listbox を包まないので D-13 と競合しない
- 退けた案: react-aria-components（初稿）。最も網羅的だが最も重く、強みである Select / ComboBox 級の部品をこの製品は自前と決めている。
  MVP で内部状態と戦った相手でもある
- 退けた案: 全部自作（ネイティブ要素 + HTML `popover` 属性）。依存はゼロになるが Popover の位置計算と Phase 2 の Dialog を自前で持つことになる
- 退けた案: Base UI。Radix 作者 + MUI で活発だが、Radix の方が実績が長い。API が近いので、乗り換えが要るときの距離は短い

### D-18. 見た目は Tailwind CSS v4 + Lightning CSS。トークンは `--bp-*` のまま

- **決定**: CSS Modules をやめ、Tailwind CSS v4（`@tailwindcss/vite`）と Vite の `css.transformer: 'lightningcss'` で組む。
  `--bp-*` トークンは `components/tokens/palette.css` に残し、`@theme inline` で Tailwind のテーマに写す。ユーティリティは
  `var(--bp-*)` を直接吐くので、ダークはトークンの再定義だけで追従する
- 守ること: 色・寸法はテーマ経由のユーティリティ（`bg-floating` `text-subtle` `p-2`）か `h-(--bp-size-row)` のようなトークン参照だけ。
  `bg-[#fff]` `w-[640px]` のような直書きは書かない。幅の分岐は `--container-*` トークンを持つコンテナクエリで行い、JS で幅を測るのは
  要素の実寸が要る箇所（フッターのヒントの溢れ）だけ
- 理由: 見た目の調整を Storybook 上で完結させたい。クラスがマークアップに並ぶ方が、CSS Modules のファイルを往復するより
  調整が速い。Lightning CSS は Tailwind v4 が内部で使っているものと同じで、CSS の変換系を 1 つに揃えられる
- 退けた案: CSS Modules + トークン（初稿）。動くが、コンポーネントごとに `.module.css` が増え、幅の分岐をコンテナクエリで書くときに
  ブレークポイントの数値をトークン化できない（`@container` はカスタムプロパティを参照できない）。Tailwind のテーマなら
  ビルド時に解決されるので、数値の置き場所が 1 つになる

### D-19. 検索 0 件のとき選択は最初の提案行に置く

- **決定**: 0 件が確定したら、選択はプレースホルダ行の位置（案内行「一致する結果がありません」）ではなく、
  その直下の**最初の提案行**（スコープを広げる › 詳細検索 › 本体検索 の先頭）に置く。案内行は `hint` で動作を持たない
- 理由: プレースホルダを置き換えた案内行に選択が残ると、`↵` を押しても何も起きない状態が既定になる。0 件で次に取る行動は
  「広げる」なので、`語 → ↵ → ↵` で広いスコープの検索が走る方が P6（同じ入力 → 同じ結果）に沿う
- 退けた案: 案内行を選択したままにする（I4 の「選択行を動かさない」の字義どおり）。I4 は非同期到着で選択を動かさない規則で、
  Enter の直接の結果として選択を置き直すのは §7.2 と同じ扱い

### D-20. スペースを横断した検索はしない。根では移動先のスペースと共通ページだけを選ぶ

- **決定**: スペースは**複数登録でき、切り替えもできる**。ただし**検索は 1 つのスペースの中だけ**（`[space]` ならそのスペース、
  `[space / project]` ならそのプロジェクト）。スコープからスペースを外した根では検索行を出さず、候補は **スペースの切り替え先**
  （`space` 行。未接続は `connect` 行）と**共通のページ**（個人設定・API キーの設定。スペース設定は admin 判定が要る可能性があり未確認）
- 理由: 技術的制約。Backlog の API はスペースごとにホストも鍵も別で、横断して 1 回で引く手段が無い。並列に投げて合流させる
  MVP の「全スペース検索はフラット」は、レートリミットと結果の整合の両面で成立しなかったので前提ごと退く
- 含意: 結果の行にスペースバッジは出ない（検索対象が 1 スペースなので）。アイコンは **スペース行とスコープパス**に出す。
  サイドパネルの「スペース」フィルターは残すが**単一選択で「全スペース」の選択肢は無い**（既定はタブのスペース）。
  進捗の帯はスペース別ではなく**種別別**（課題・Wiki・ドキュメント）。検索状態の URL（§7.6）はスペースの URL に載るので影響しない
- 未確認: スペース設定への共通ページを出すかは admin かどうかで変わりうる。M3 の実機確認で決める（`backlog-facts.md` に追記する）

### D-21. Backlog 本体のテキスト入力にフォーカスがあるときは `⌘K` を捕捉しない（仮の境界）

- **状況**: `commands` を使わない（D-10）ので、`⌘K` は content script の keydown で捕捉する。Backlog 本体のエディタや
  `⌘K` を使う画面との境界は実機で確認するまで決められない（未決 #4、`milestones.md` M3 の人の工程）
- **仮の決定**: フォーカスが `input`（ボタン・チェックボックス等の非テキスト型を除く）・`textarea`・`contenteditable` に
  あるときは捕捉せず、ページに `⌘K` を通す。それ以外の場所では捕捉する。変換中（`isComposing`）は場所を問わず捕捉しない（I5）
- **推奨**: 実機確認の結果、Backlog のエディタが `⌘K` にリンク挿入などを割り当てていれば仮の境界をそのまま採る。
  割り当てが無ければ**テキスト入力でも捕捉する**方へ広げる。P1（覚えるのは `⌘K` だけ）は「どこで押しても開く」ことを
  含み、入力欄にいるときだけ効かない例外は 3 番目の想定ユーザーを迷わせる
- 退けた案: 捕捉しない領域をセレクタで列挙する（Backlog の DOM に依存し、本体の更新で壊れる）。`commands` に
  戻す（D-10 で退けた理由がそのまま残る）
- 判定の実装は `lib/hotkey/paletteHotkey.ts` の `isTextEntryTarget`。E2E「テキスト入力にフォーカスがあるとき `⌘K` は
  ページに届く」がこの境界を固定している。境界を動かすときは E2E も一緒に動かす

### D-22. ツールバーのアイコンに popup を持たない

- **決定**: `action.default_popup` を置かず、クリックは Service Worker の `action.onClicked` が受けて
  Backlog のタブならサイドパネル（Firefox はサイドバー）、それ以外は設定画面を開く（`surfaces.md` §4）。
  WXT の雛形にあった `entrypoints/popup/` は消す
- 理由: popup を置くと `action.onClicked` が発火しなくなり、§4 の「押した場所で振る舞いを変える」経路が作れない。
  パレットは `⌘K`、詳細検索はサイドパネル、設定は設定画面と面が決まっていて、popup に載せる内容が無い
- 退けた案: popup にミニパレットや設定へのリンクを置く。Backlog 外で `⌘K` を使わせないという D-10 の判断と
  同じ理由で、Backlog 外での起動経路を増やさない

### D-23. Firefox のアドオン ID は `backlog-palette@simochee.github.io`

- **決定**: `browser_specific_settings.gecko.id` を上記に固定する。AMO の必須項目で、一度公開すると
  変えられない（変えると別のアドオンになり、既存の利用者に更新が届かない）
- 理由: リポジトリの公開先（GitHub Pages のホスト）を持ち主として使えば、他者と衝突せず、後から所有を示せる
- 退けた案: GUID 形式（`{…}`）。衝突はしないが所有者が読めない。ストア提出時に別 ID を求められたら §3 に記録して差し替える
### D-26. 表示キャッシュ由来の行は「強いローカル一致」に数えない

- **決定**: 自由語のときに候補を検索行より上に出す「強いローカル一致」（palette.md §4）は、名前が安定している候補
  （ページ定義・プロジェクト・スペース・コマンド）の前方一致以上だけで判定する。表示キャッシュにある課題・Wiki・
  ドキュメントは件名が前方一致しても検索行の下に置く
- 理由: P6（筋肉記憶を壊さない）。キャッシュの中身は開いたページで日々変わるので、キャッシュの課題を検索行より上に
  置くと「同じ語 → ↵」の結果が日によって変わる。ページ定義やプロジェクトは集合が有限で名前が変わらないため、
  前方一致がそのまま目的地の確定になる。M1 の S4（「ログイン」で検索行が先頭、キャッシュの課題はその下）はこの規則の形
- 退けた案: キャッシュも前方一致なら強い一致に数える（§4 の字義どおり）。`ログイン` と打って ↵ したときに、昨日開いた
  課題が開く日と検索が走る日ができる
- 起票: 2026-09-13、M2 の derive 実装時

### D-27. 「最近開いた」はスコープのスペースの中だけ。未接続でも出す

- **決定**: 空状態の「最近開いた」（palette.md §9）は、スコープが `[space]` / `[space / project]` のとき
  そのスペースの表示キャッシュ・プロジェクトだけから組む。別スペースで開いた課題は出さない。根では
  「最近開いた」自体を出さない（§9 の根はスペースの移動と共通ページだけ）。未接続のスペースでも
  「最近開いた」は出す。表示キャッシュと行動ログだけで組めて API を使わないため、§9 の「出せるもの」に含まれる
- 理由: D-20 の含意。パレットはスペースの中で動き、結果の行にスペースバッジも出さないので、別スペースの
  課題が混ざると行のプロジェクト名だけでは判別できない。未接続で出さないと、接続前に開いていた履歴が
  接続導線の手前で消え、「接続へ運ぶ」だけの面になる
- 退けた案: 根で全スペースの「最近開いた」を出す。根は移動先を選ぶ面で、行を選んで遷移する面ではない
- 起票: 2026-09-13、M5 の E2E（S0〜S13）で解釈違いが見つかった

### D-31. API キーは backlog-js のヘッダ認証で送り、fetch の差し替えで観測と退避を行う

- **決定**: `backlog-js` 0.20.1 は `apiKey` を渡すと `Backlog-API-Key` **ヘッダ**で送る（`?apiKey=` は付けない）ので、
  そのまま使う。ラッパー `lib/backlog/client.ts` は `fetch` を差し替えて、撃つ前にレート枠を取り（`acquire`）、
  応答の `X-RateLimit-*` を残数に反映する。ヘッダが CORS のプリフライトを通らないと実機で分かったとき
  （`backlog-facts.md` §5-15）の退避は、同じ差し替え fetch がヘッダをクエリへ移す形で `API_KEY_TRANSPORT` の
  定数 1 つで切り替える
- 理由: リクエストを自前で組むと backlog-js のパスとパラメータの知識を二重に持つことになる。fetch はもともと
  注入できる口で、観測（ヘッダ読み）と退避（クエリ移し）の両方を 1 箇所に閉じられる
- 退けた案: リクエストを自前で組む（backlog-js を型だけに使う）。エンドポイントの追加ごとにパスを書く手間が増え、
  公式クライアントを採った理由（T-4）が薄れる
- 退けた案: backlog-js の `request()` を直接呼んで Response を受ける。`get<T>()` などの型付きメソッドを捨てることになる
- 起票: 2026-09-13、M4 PR 1

### D-33. Firefox の埋め込み iframe では fetch を background に委譲する

- **状況**: Firefox では Web ページに埋めた拡張 iframe で `browser.tabs` が undefined になり、fetch は CORS を受ける
  （matches のホスト権限が効かない。B の Firefox スパイク、● 2026-09-13）。`tech-stack.md` §5-16 の退避が Firefox で要る
- **決定**: 委譲点は D-31 の差し替え fetch に渡す `fetchImpl` の 1 箇所（`lib/backlog/platformFetch.ts`）。`browser.tabs` が
  無いコンテキストだけ `runtime.sendMessage` で background に `{ url, method, headers, body }` を送り、background が fetch して
  `{ status, statusText, headers, body }`（`X-RateLimit-*` を含む）を返す。Chrome・サイドパネル・設定画面は直接撃つ。
  レート制御は storage 共有なのでページ側のまま動く
- メッセージは `@webext-core/messaging` 4.0.0。protocol は `lib/messaging/background.ts`（B の tabs 委譲と同じ場所）。
  background 側のハンドラは Backlog のスペースの origin だけを受け、任意 URL の中継にしない
- 鍵は background に**渡さない**設計だが、差し替え fetch はヘッダに鍵を載せた Request を送るので結果として鍵が background を
  通る。background は拡張オリジンの内側（I7 の境界内）なので許容する。background ではリクエストの内容をログに出さない
- 退けた案: Firefox でも常に background 経由にする。Chrome で不要な往復が増え、T-2（拡張ページから直接）の判断を崩す
- 退けた案: 環境判定を `navigator.userAgent` で行う。権限の有無が本質で、`browser.tabs` の有無がそれを直接表す
- 起票: 2026-09-13、リードの裁定。E2E は Chrome では通れないので、B の Firefox E2E（Puppeteer BiDi）に接続導線を足す

### D-34. 拡張 iframe の web_accessible_resources は https 全体に開き、検出は use_dynamic_url で防ぐ

- **状況**: カスタムドメイン（`surfaces.md` §8）は利用者が設定画面で足すので、content script は
  `scripting.registerContentScripts` で動的に登録できる。しかし `web_accessible_resources.matches` は
  manifest の静的な値で、実行時に足せない。静的な 3 ドメインだけに絞ると、カスタムドメインのページで
  パレットと貼り付けバーの iframe が読めない
- **決定**: `matches` を `https://*/*` にする。ページ側からの拡張の検出は `use_dynamic_url: true` が防ぐ
  （URL がセッションごとに変わり推測できない）。content script が注入されるページは静的な matches と
  動的登録で絞られたままなので、iframe を作る側は変わらない
- 退けた案: カスタムドメインの iframe だけ別の仕組み（ページ側 DOM）で出す。鍵がページのコンテキストを
  通る（§1.1 の禁止事項）
- 退けた案: 任意のホスト権限（`optional_host_permissions`）で `matches` も広がることを期待する。仕様上、
  web_accessible_resources の matches は権限とは別で、実行時に変わらない
- 起票: 2026-09-13、M4 PR 5

### D-50. 期限は急ぎのときだけ行に出す。並びは変えない

- **決定**: 担当中の課題の行に、**期限切れ**（`期限切れ`、危険色）と**7 日以内**（`期限 9/25`、警告色）のときだけ
  期限のバッジを出す。8 日以上先は出さない。並びは更新日時順のまま変えない
- 理由: ディレクター・営業事務は「更新された順」より「締切が迫っている順」で動く。ただし並べ替えは
  P6（同じ入力 → 同じ結果 → 同じ位置）を日付で壊すので採らない。**並びは変えず、急ぎを見つける手がかりだけを行に置く**。
  すべての期限を出すと 5 行の大半が意味を持たないバッジを抱え、密度だけが上がる
- 追加のリクエストは要らない。`GET /api/v2/issues` の応答に `dueDate` が含まれる（`backlog-facts.md` §3.2、◎）
- 退けた案: 期限順に並べ替える。P6 に反し、「昨日と同じ操作で同じ場所」が成立しなくなる
- 起票: 2026-09-22、キャプチャレビュー 2 周目

### D-51. 狭幅では種別タグと `⇥` を畳む

- **決定**: `< 400px`（`@max-narrow`）で、行の種別タグ（`バグ` `タスク`）と行末の `⇥` を隠す。
  `↵` と `›`、ステータスのマーカーは残す
- 理由: 幅 360 では種別タグ + 課題キーが 1 行目の 40% を取り、件名が 3〜5 文字しか残らない。
  §12 は既にこの幅で「行の補足を隠しマーカーだけ残す」と決めており、同じ段の判断。
  行が何であるかは種別アイコンが先頭で言っている
- P5（ヒントは省かない）との関係: 省くのは `⇥` だけで、`↵`（何が起きるか）は残る。
  `⇥` の補完は入力を速くする加速装置で、それが要る人は幅を広げられる
- 起票: 2026-09-22、キャプチャレビュー 2 周目

### D-52. URL の同一性は `lib/nav/path.ts` が 1 箇所で持つ。表示キャッシュは正規形で保存する

- **決定**: 「2 つの URL が同じページを指すか」の判定を `canonicalPath` / `canonicalUrl` に集約する。
  表示キャッシュ・行動ログ・現在ページの比較は、すべてこの正規形で行う
- **畳むもの**: 末尾のスラッシュ、課題キーの大文字小文字、旧形式のパス（`.action` の別名）、
  表示状態のクエリ（`/find/PROJ?statusId=2`）、フラグメント（`#comment-12`）
- **畳まないもの**: Wiki のページ名（大文字小文字も末尾スラッシュもエンコードも区別する値。
  デコードして組み直すと階層の `/` が `%2F` になり別ページになる）、ドキュメント ID、
  プロジェクト設定の `?project.key=`（パスに識別子が無く、クエリが識別子。落とすと PROJ と MOB が同じ URL になる）
- **`displayCache` は version 3 に上げ、保存済みの URL を正規形に畳む**
- 理由: 正規化が無いと `isHere`（D-37）が効かない場面が残るだけでなく、**旧 URL と新 URL が
  両方残って同じ課題が「最近開いた」に 2 行並ぶ**。`pushVisit` は URL で重複を畳むので、
  書き方が違えば別の行になり、TTL 90 日のあいだ続く。移行が必要なのはこの 2 行問題のため
- 守り: `recentSection` でも同じ行 id を 1 つに畳む。移行が走らない経路でも 2 行にしない
- **別名 Wiki（`/alias/wiki/{id}`）を記録に含める**: これまで記録されず、その形式で開いた Wiki は
  一度も「最近開いた」に載らなかった（Backlog 自身のリンクは別名形式が多い）。`key` は数字列の id。
  `lib/backlog/entries.ts` の `wikiEntry` と行動ログが既にこの形なので、検索経由の頻度と初めて合算される
- **束ねない**: `/alias/wiki/{id}` と `/wiki/{KEY}/{name}` が同じ Wiki かは `GET /wikis/{id}` にしか
  答えが無く、空状態の 100ms 予算の外。同じ Wiki を両方の形式で開いた人だけ 2 行に見える。
  これは名前形式が記録される限り元から起き得たもので、別名を拾うことで新しく生まれる問題ではない
- 含意: `DisplayCacheEntry.projectKey` と `CachedEntry.projectId` / `projectName` は optional になる。
  別名 Wiki の URL はプロジェクトを含まない
- 未確認: Backlog が `/alias/wiki/{id}` を名前形式へリダイレクトするか（`backlog-facts.md` §5 に追記）。
  どちらでも実装は同じで、2 行に見える頻度だけが変わる
- 起票: 2026-09-22、キャプチャレビュー 2 周目の「規則の穴」

### D-53. 未接続でも先頭行は「行き先」。接続行は末尾のまま

- **決定**: 未接続のスペースの空状態は `[最近開いた, ページ, 接続]` の順のまま。接続行を先頭に上げない。
  出せるものが何も無いとき（S0）だけ接続行が 1 行だけ残る
- 理由: 先頭行は D-37 で「直前に見ていたもの」＝戻る先にし、D-46 でも先頭を譲らないと決めた。
  `⌘K` → `↵` の意味が「行く」で一定であることが P6 の土台になっている。
  接続は一度きりの設定で、毎回の `↵` を占める種類の操作ではない。
  未接続でもページ移動と「最近開いた」は動く（D-27）ので、パレットは接続前から役に立つ
- 退けた案: 未接続のときだけ接続行を先頭に置く。`⌘K` → `↵` の着地がスペースの状態で変わる。
  接続していないことに気づかない懸念はあるが、接続行は常に見えており、検索と担当課題を
  使おうとした時点でそれぞれの行が接続へ運ぶ（§7.5・D-45）
- 起票: 2026-09-22、キャプチャレビュー 最終確認

### D-56. 貼り付けバーは接続の成立をページへ `connected` で知らせ、URL から `#bp-connect` を外す

- **決定**: iframe → ページの通信に `{ t: 'connected' }` を足す。送るのは貼り付けバーだけで、中身は種別のみ
  （スペース名も鍵も載せない）。受けた content script は `history.replaceState` で `#bp-connect` を外す
- 理由: フラグメントが残ると、接続後に再読み込みしたとき貼り付けバーが出直す。親ページの URL を触れるのは
  content script だけで、接続できたかを知っているのは拡張ページだけなので、知らせる手段が要る
- 安全性: 受け手は従来どおり送り主の window と拡張の origin を確かめる。偽の `connected` を届けられても
  起きるのはフラグメントが外れることだけで、鍵にもスペースの選択にも関わらない（I7）
- 退けた案: バーを出した時点でフラグメントを外す。接続前に再読み込みするとバーが出なくなり、
  パレットからやり直すことになる
- 退けた案: `close` で外す。完了表示を閉じる前に再読み込みすると残り、接続せずに閉じたときも外れてしまう
- 退けた案: `location.hash` を書き換える。履歴が積まれ、戻るとバーが出直す
- 起票: 2026-09-23

### D-57. パレットのテーマは Backlog 本体に揃える

- **決定**: Backlog の `<html>` に `dark-mode` があればダーク、無ければライト。`settings.theme` はパレットでは見ない
  （サイドパネルは Backlog のページに属さないので、従来どおり設定と OS に従う）。content script が
  クラスを読み、iframe の URL（`?colorScheme=`）と `open` の `PageContext.colorScheme` で渡す
- 理由: パレットは Backlog の画面の上に重なる。本体とテーマが食い違うと浮いて見え、OS 追従では
  Backlog 側でテーマを選んでいる人に合わない
- 2 経路にする理由: `open` は iframe を表示した後に非同期で届く。これだけだとダークの Backlog で最初の
  `⌘K` に一瞬ライトが写る。URL だけだと、読み込み後に本体側で切り替えたときに追従しない
- 安全性: 値は `'dark'` のときだけダーク、それ以外はライトに倒す。偽の値を届けられても変わるのは配色だけ（I7）
- 退けた案: テーマ変更を知らせるメッセージ種別を足し、`MutationObserver` で送る。開いている間に切り替わる
  場面はほぼ無く、通信路を広げるほどの利点が無い
- 起票: 2026-09-23

### D-58. パレットはページで解決された Backlog のテーマ変数を `theme` で受け、トークンから直接参照する

- **決定**: ページ → iframe の通信に `{ t: 'theme', theme }` を足す。content script が `body` の computed style から
  Backlog のテーマ変数（`../backlog-facts.md` §7）を読み、値がライトとダークのどちらのものかを添えて、iframe の読み込み時・
  `wxt:locationchange`・開く直前に送る。iframe は受けた値を検証し直し、**同じ変数名のまま**ルートに置く。
  `components/tokens/backlog-theme.css` が `--bp-accent: var(--defaultColorAccent)` のように直接参照し、当て方は
  Backlog 本体での使い分け（§7.2）に合わせる。パレットの配色がページと違うときと、変数が揃わないページでは既定の配色
- 色はこちらで持たない: Backlog の値を加工（明度の調整・文字色の自動選択）せずに使う。テーマの 14 色とダークモードの値は
  Backlog 側が持っており、こちらで作り直すと Backlog の変更に追従できない。プロジェクト外のページでは `:root` の既定（緑）
  が解決されるので、フォールバックも Backlog の値になる
- 理由: パレットは Backlog の上に重なって開く。プロジェクトごとに色を変えている利用者にとって、今どのプロジェクトに
  いるかを配色でも示せる。拡張のオリジンの iframe からはページの CSS を読めないので、読めるのは content script だけ
- `open` に載せない理由: iframe は `display:block` の後に `open` を受ける。postMessage は非同期なので、`open` に
  載せると表示された最初のフレームが既定の配色で描かれる。先回りして送るために別の種別にする
- 配色が違うときに当てない理由: Backlog のライトの値は白地、ダークの値は暗い面の上で使う前提の色。
  D-57 でパレットの配色はページに揃うが、配色は `open` と URL で、テーマ変数は `theme` で別々に届くので、
  片方だけが古い間に当てると前提が崩れる。値の配色は D-57 と同じ `<html>` の `dark-mode` で判定し、両者の食い違いを作らない
- 安全性: ページのスクリプトも同じ window から送れるので、届く値はページが選べる。起きうるのはパレットの配色が
  変わることだけで、鍵にもスペースの選択にも関わらない（I7）。値は Backlog が宣言する形（`#rrggbb` と `r,g,b`）に
  絞ってから style に置く
- 退けた案: 拡張の設定でテーマ色を選ばせる。プロジェクトごとの色はページがすでに持っており、二重に管理させることになる
- 退けた案: ReactApp.css のテーマ表を拡張に写し、`body` のクラス名だけを送る。Backlog の版上げで色が変わると追従できない
- 起票: 2026-09-23

### D-59. 接続の回復は `online` イベントで知り、開いている面だけが引き直す

- **決定**: 表示中の検索がオフラインで終わっていて、パレットが開いている（パネルは表示中の）ときだけ
  `online` を聞き、同じ語・スコープ（パネルは条件も）で引き直す。自動の引き直しは検索回数と
  0 件率（surfaces.md §10）に数えず、パネルは検索履歴にも積まない
- `online` が発火しない切断は自動では引き直さない。VPN 断・DNS の失敗・CORS の拒否・background の不通は
  `navigator.onLine` が true のまま fetch が落ちてオフラインになる（lib/backlog/failure.ts の TransportError）。
  このとき検索行の `↵` がそのまま引き直しになるので、「接続すると再検索します」の文言は変えない
- 理由: 閉じたパレットも iframe は描き続けており、Backlog のタブの数だけある。開閉を見ずに聞くと、
  接続が戻った瞬間にタブの数だけ search 枠を使う。利用者が打っていない検索を計測に入れると 0 件率が歪む
- 退けた案: 一定間隔で引き直す。オフラインの間 search 枠を使い続け、回復したかどうかは結局 fetch の成否でしか分からない
- 退けた案: 画面にフォーカスが戻ったときにも引き直す。切り替えのたびに API を叩き、`↵` と役割が重なる
- 範囲外: 担当中の課題の取得がオフラインで終わったとき（palette.md §9）は引き直さない。§9 は
  「オフラインです。接続すると再検索します」と書くが、ラベル `assignedOffline` は再検索を約束しておらず、
  仕様とラベルが既にずれている。どちらに揃えるかは別に決める
- 起票: 2026-09-23、オフライン誤表示の調査から
